# Data Quality Audit

I found no high-risk problems. The brief counts items by status and groups them by order month, category and brand, so most of these issues only touch columns we don't use. The two that can change the ranking are the 5 items with no matching product and the 5 misspelled categories. Both are tiny, and both can be fixed with simple rules.

## Issues to fix

| Severity | Table.column | Rows | What is wrong | Proposed rule |
|---|---|---|---|---|
| low | `order_items.product_id` | 5 | Five items point to products that do not exist (IDs 30001 to 30005). We can't tell their category or brand. They would drop out of the category and brand ranking but could still be counted in the company-wide rate. That would make the totals disagree. The effect is tiny. | Exclude order items whose product_id is not in products.id from every KPI, including the company-wide benchmark, so all views use the same base. Log the excluded count. |
| low | `products.category` | 5 | Five products have a category spelled differently, such as 'JEANS', 'jeans ', 'Sweater', 'Tops and Tees' and 'Accesories'. They are the same categories as the main spellings. Left alone, they would show up as extra tiny categories. They would also be left out of the real category counts. Only 5 products are affected, so the impact is small. It is still wrong in a dimension we rank on. | Trim spaces and map to the standard names: JEANS and 'jeans ' to Jeans, 'Tops and Tees' to 'Tops & Tees', Sweater to Sweaters, Accesories to Accessories. Apply this before grouping. Also check brand for the same problem. |
| low | `order_items.sale_price` | 5 | Five items have a zero or negative sale price, which is not valid for a sale. No KPI in the brief uses price, because return rate is counted in items. These rows do not distort the numbers today. They would distort any money measure if one were added later. They could also be test rows or refund lines. | Keep these rows for item-count KPIs, since status decides whether an item counts. Exclude order items with sale_price <= 0 from any future money-based measure. Flag them to the data owner. |
| low | `order_items.created_at, returned_at` | 637 | 637 returned items have a return time before the order time. The timestamps are wrong. The brief assigns items to months by order date and counts returns by status, so the counts do not change. It does confirm that returned_at should not be used. The month by return date would be unreliable. | Count a return from the item status, not from returned_at. Assign the month from created_at. Do not calculate any time-to-return measure from these rows. |
| low | `order_items.created_at, delivered_at` | 5,761 | 5,761 items show a delivery time before the order time. The timestamps are wrong. The brief does not use delivered_at. It decides delivered items by status and groups by order date. The numbers are safe as long as status is used. | Use the status field to decide which items are delivered. Do not use delivered_at for filtering or for month assignment. Do not report delivery-time measures from this column. |
| low | `order_items.created_at, shipped_at` | 33,766 | 33,766 items show a shipping time before the order time. This is a large share, so the shipping timestamps cannot be trusted. The brief does not use shipped_at. It only needs status and order date, so the KPIs are not affected. | Do not use shipped_at in this dashboard. Use status to exclude items that are still processing or shipped. Report the issue to the data owner. |
